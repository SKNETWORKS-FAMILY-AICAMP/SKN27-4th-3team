# 오너 결정 워크시트

이 문서는 사용자가 직접 선택해야 하는 설계 결정을 모아두는 워크시트다.

아래 항목은 확정값이 아니다. 각 결정은 사용자가 `selected_option`을 지정한 뒤에만 공식 문서로 옮긴다.

빠르게 검토하려면 [[08_Implementation_Contracts/04_추천_선택_세트]]의 추천 묶음을 먼저 보고, 승인하거나 수정한다.

## 사용 방법

1. 각 결정 항목의 `option_id`를 읽는다.
2. 마음에 드는 선택지가 있으면 `selected_option`에 해당 ID를 적는다.
3. 선택지가 마음에 들지 않으면 새 옵션을 추가한다.
4. 선택된 항목만 `docs`의 공식 설계 문서와 `api-spec`의 승인 명세로 승격한다.

## 상태 값

| 상태 | 의미 |
|---|---|
| undecided | 아직 선택하지 않음 |
| selected | 사용자가 선택함 |
| rejected | 사용자가 제외함 |
| needs_revision | 옵션을 다시 작성해야 함 |

## D-001. 이 폴더의 역할

status: `selected`  
selected_option: `D-001-C`

### 결정

검토안과 승인본을 분리한다.

적용 제약:

- `docs/08_Implementation_Contracts`는 결정 전 검토안과 논의 기록만 담는다.
- 사용자가 승인한 항목만 별도 승인본 폴더로 옮긴다.
- 팀 공유용 기준 문서는 승인본 폴더를 우선한다.

### 선택지

| option_id | 선택지 | 설명 | 영향 |
|---|---|---|---|
| D-001-A | 검토안 폴더 유지 | 현재 `08_Implementation_Contracts`는 결정 전 검토안만 담는다. | 팀원이 확정으로 오해할 위험이 낮다. 공식 문서 승격 작업이 별도로 필요하다. |
| D-001-B | 공식 계약 폴더로 승격 | 사용자가 승인한 뒤 이 폴더를 프론트/백엔드 공통 기준으로 쓴다. | 팀에게 전달하기 쉽지만, 미확정 항목을 모두 정리해야 한다. |
| D-001-C | 검토안과 승인본 분리 | `08_Implementation_Contracts`는 검토안, 별도 `09_Approved_Contracts`를 승인본으로 둔다. | 가장 안전하지만 문서가 늘어난다. |

### 내 추천

`D-001-C`. 지금은 미확정이 많아서 검토안과 승인본을 분리하는 편이 팀 커뮤니케이션에 안전하다.

## D-010. 프론트 세계관 기준의 수준

status: `selected`  
selected_option: `D-010-CUSTOM-A-GUARDRAILS`

### 결정

큰 톤만 제공하되, 최소 금지선을 함께 둔다.

적용 제약:

- 프론트팀에는 세부 상태 표현 방식까지 강제하지 않는다.
- 프론트팀은 화면, 레이아웃, 상태 시각화, 애니메이션, 문장 배치에서 넓은 자유도를 가진다.
- 단, 아래 최소 금지선은 지킨다.

### 최소 금지선

1. 카드 배틀, 스킬 버튼 전투, 판타지 RPG 전투 UI처럼 보이게 만들지 않는다.
2. 가챠, 보상 뽑기, 환금성 재화, 사행성 결제처럼 보이는 표현을 쓰지 않는다.
3. LLM 채팅 게임처럼 보이게 만들지 않는다. 플레이의 중심은 자유 대화가 아니라 서버 판정형 의식 결투다.
4. 프론트가 승패, 수치 변화, 단서 진위, 봉인 가능 여부를 임의로 결정하지 않는다.
5. 서버 응답과 충돌하는 문구를 화면에 표시하지 않는다.
6. 괴이를 체력 게이지로 깎아 죽이는 구조처럼 표현하지 않는다. 목표는 진명을 파헤치고 봉인하는 것이다.
7. 결과 화면에서 LLM 생성 문장이나 프론트 문구를 서버 판정 결과처럼 위장하지 않는다.

### 선택지

| option_id | 선택지 | 설명 | 영향 |
|---|---|---|---|
| D-010-A | 큰 톤만 제공 | 생존 의식 테이블, 공포 미스터리, 서버 판정 원칙만 제공한다. | 프론트팀 창의성이 넓다. 화면 간 톤 차이가 커질 수 있다. |
| D-010-B | 톤 + 상태 표현 제공 | 이성/의식력/저주 흔적/단서의 표현 방향까지 제공한다. | 프론트팀이 빠르게 맞출 수 있다. 일부 시각 선택이 제한될 수 있다. |
| D-010-C | 톤 + 상태 표현 + 문장 초안 제공 | 브리핑/승리/패배 문장 초안까지 제공한다. | 목업 속도가 빠르다. 사용자가 문장 톤을 별도로 승인해야 한다. |

### 내 추천

`D-010-B`. 프론트팀이 구현을 시작하기에는 상태 표현 기준이 필요하지만, 문장까지 확정하면 사용자의 창작 결정이 너무 빨리 닫힌다.

## D-020. 첫 괴이 문장 작성 방식

status: `selected`  
selected_option: `D-020-B`

### 결정

사람이 기준 문장을 작성하고 승인한다. LLM은 승인된 기준 문장을 바탕으로 판정 이후 변형/요약만 만든다.

적용 제약:

- 브리핑, 승리 기록, 패배 기록의 공식 기준 문장은 사람이 작성하고 사용자가 승인한다.
- LLM은 공식 기준 문장을 새로 확정하지 않는다.
- LLM은 결과 화면 요약, 스타일 요약, 운영자용 로그 요약처럼 판정 이후 보조 문장에 먼저 사용한다.
- LLM 생성 문장은 서버 판정 결과를 바꾸지 않는다.
- LLM 생성 문장은 공식 설정 추가나 룰 변경으로 취급하지 않는다.

### 선택지

| option_id | 선택지 | 설명 | 영향 |
|---|---|---|---|
| D-020-A | 정적 공식 문장 직접 작성 | 브리핑/승리/패배 문장을 사람이 직접 확정한다. | 가장 안정적이다. LLM 품질에 의존하지 않는다. |
| D-020-B | 사람이 기준 문장 작성, LLM은 변형만 생성 | 공식 문장은 사람이 고정하고 LLM은 결과 화면 변형 문장만 만든다. | 안정성과 다양성을 같이 얻는다. LLM 검수/로그가 필요하다. |
| D-020-C | RAG+LLM으로 문장 후보 생성 후 승인 | 세계관 문서를 검색해 LLM이 문장 후보를 만들고 사람이 고른다. | 창작 속도는 빠르지만 승인 절차가 필요하다. |

### 내 추천

`D-020-B`. 첫 MVP는 문장 안정성이 중요하므로 공식 기준 문장은 사람이 잡고, LLM은 판정 이후 보조 문장부터 붙이는 편이 안전하다.

## D-030. 진명 조각 reveal 방식

status: `selected`  
selected_option: `D-030-B`

### 결정

진명 조각은 행동 상성 결과와 괴이별 조건을 함께 보고 획득한다.

적용 제약:

- `game_rules`는 공통 행동 상성 결과와 단서 진척 후보를 계산한다.
- `story`는 현재 괴이, 금기, 정보 대상, 이전 행동 기록 등 괴이별 조건을 검사한다.
- 최종 진명 조각 획득 여부는 서버가 결정한다.
- 프론트는 진명 조각 획득을 예측하거나 임의 확정하지 않는다.
- `거울 속의 손님`은 공통 상성 결과뿐 아니라 기억, 거울, 반복 질문 금기와 연결된 조건을 가질 수 있다.

### 선택지

| option_id | 선택지 | 설명 | 영향 |
|---|---|---|---|
| D-030-A | 행동 상성 결과로만 reveal | 특정 상성 결과가 나왔을 때 진명 조각을 얻는다. | 구현이 단순하다. 스토리별 개성이 약할 수 있다. |
| D-030-B | 행동 상성 + 괴이별 조건 | 상성 결과에 더해 `거울 속의 손님` 전용 조건을 검사한다. | 사건 개성이 살아난다. 서버 조건 설계가 필요하다. |
| D-030-C | 누적 조사 점수 기반 | 간파/계약 등으로 조사 점수를 쌓고 임계점마다 reveal한다. | 밸런싱이 편하다. 직관적인 한 턴 결과가 약해질 수 있다. |

### 내 추천

`D-030-B`. 공통 룰과 첫 괴이 개성을 동시에 살릴 수 있다.

## D-040. 거짓 단서 trigger 방식

status: `selected`  
selected_option: `D-040-B`

### 결정

거짓 단서는 속임수 결과와 괴이별 금기 위반으로 생성한다.

적용 제약:

- 최종 거짓 단서 생성, 공개, 제거 여부는 서버가 결정한다.
- 프론트는 단서가 거짓인지 임의로 확정하지 않는다.

| option_id | 선택지 | 설명 | 영향 |
|---|---|---|---|
| D-040-A | 속임수 실패/성공 결과에만 생성 | 상성표의 `속임수` 결과로만 거짓 단서를 만든다. | 명확하지만 괴이 개성이 약하다. |
| D-040-B | 속임수 + 금기 위반으로 생성 | 속임수 결과와 `같은 질문 반복` 금기 위반이 거짓 단서를 만든다. | 첫 괴이 정체성과 잘 맞는다. 금기 추적이 필요하다. |
| D-040-C | 괴이 행동 정책이 별도 생성 | 괴이의 가중치 정책이 특정 조건에서 거짓 단서를 생성한다. | 다양하지만 디버깅이 어려울 수 있다. |

### 내 추천

`D-040-B`. `거울 속의 손님`의 기억 왜곡 컨셉과 가장 잘 맞고 프론트에도 설명하기 쉽다.

## D-100. API 명세 포맷

status: `selected`  
selected_option: `D-100-B`

### 결정

API 명세는 설명용 JSONC 원본과 도구용 strict JSON 생성본을 함께 관리한다.

적용 제약:

- 사람이 읽고 논의하는 원본은 주석이 들어간 `.jsonc`로 둔다.
- 프론트 타입 생성, mock server, validation 등 도구 연동용 파일은 주석 없는 `.json`으로 생성한다.
- 생성본 JSON을 사람이 직접 수정하지 않는다.
- API 내용이 확정되기 전까지 생성본도 proposal/review 상태임을 표시한다.
- API 확정 후에는 승인본 명세를 별도 파일로 만든다.

### 선택지

| option_id | 선택지 | 설명 | 영향 |
|---|---|---|---|
| D-100-A | JSONC 원본만 유지 | 주석 많은 JSONC를 사람이 읽는 기준으로 둔다. | 설명력이 높다. 도구 자동화는 약하다. |
| D-100-B | JSONC 원본 + strict JSON 생성 | JSONC는 설명용, JSON은 프론트/백엔드 도구용으로 둔다. | 가장 균형적이다. 변환 스크립트가 필요하다. |
| D-100-C | OpenAPI로 바로 작성 | OpenAPI 3.x를 기준으로 명세한다. | 도구 호환성이 좋다. 초반 작성 부담이 크다. |

### 내 추천

`D-100-B`. 지금처럼 설명이 중요한 단계에서는 JSONC가 좋고, 이후 자동화에는 strict JSON이 필요하다.

## D-110. API 응답 envelope

status: `selected`  
selected_option: `D-110-A`

### 결정

모든 API 응답은 성공 시 `{ data, meta }`, 실패 시 `{ error, meta }` 형태로 감싼다.

적용 제약:

- 성공 응답 payload는 `data` 아래에 둔다.
- 요청 추적, 서버 시간, pagination 등 보조 정보는 `meta` 아래에 둔다.
- 실패 응답은 `error.code`, `error.message`, `error.details`를 사용한다.
- 프론트는 사용자 표시 문구를 `error.code` 기준으로 매핑할 수 있다.
- endpoint마다 응답 형태를 임의로 바꾸지 않는다.

### 선택지

| option_id | 선택지 | 설명 | 영향 |
|---|---|---|---|
| D-110-A | `{ data, meta }` / `{ error, meta }` | 모든 응답을 동일한 envelope로 감싼다. | 일관성이 좋다. 작은 응답도 다소 장황해진다. |
| D-110-B | 성공은 direct body, 실패만 `{ error }` | 성공 응답은 바로 payload를 반환한다. | 단순하다. 페이지네이션/trace 확장이 흩어질 수 있다. |
| D-110-C | endpoint별 자율 | 각 API가 필요한 형태를 쓴다. | 빠르지만 팀 전체 일관성이 떨어진다. |

### 내 추천

`D-110-A`. 초반 협업에서는 장황함보다 일관성이 더 중요하다.

## D-120. Auth access token 전달 방식

status: `selected`  
selected_option: `D-120-B`

### 결정

access token과 refresh token을 모두 HttpOnly cookie로 전달한다.

적용 제약:

- 프론트는 access token과 refresh token을 직접 저장하거나 읽지 않는다.
- localStorage/sessionStorage에 token을 저장하지 않는다.
- 인증 요청은 cookie 기반으로 처리한다.
- cookie 기반 인증이므로 CSRF 정책을 별도로 확정해야 한다.
- 로컬 개발 환경에서 Secure cookie 처리 방식을 별도 설계해야 한다.

### 선택지

| option_id | 선택지 | 설명 | 영향 |
|---|---|---|---|
| D-120-A | access body + refresh HttpOnly cookie | access token은 body로 받고 메모리에만 저장한다. refresh는 HttpOnly cookie. | 프론트 구현이 쉽다. XSS 상황의 access token 노출 리스크를 관리해야 한다. |
| D-120-B | access/refresh 모두 HttpOnly cookie | JS가 token을 직접 다루지 않는다. | 보안성이 좋다. CSRF 설계와 개발 편의 조율이 필요하다. |
| D-120-C | BFF 세션 방식 | 프론트는 토큰을 전혀 모르고 백엔드 세션/BFF를 쓴다. | 보안과 운영은 좋지만 구조가 커진다. |

### 내 추천

`D-120-B`를 장기 목표로 검토하되, 개발 속도가 중요하면 `D-120-A`를 MVP 후보로 둘 수 있다.

## D-130. CSRF 정책

status: `selected`  
selected_option: `D-130-B`

### 결정

모든 state-changing endpoint에 CSRF를 적용한다.

선택 이유:

- access token과 refresh token을 모두 HttpOnly cookie로 전달하기로 했으므로 cookie 기반 요청 보호가 중요하다.
- 본사 평가에서 상품성뿐 아니라 시스템 완성도와 보안 설계 일관성이 중요하다.
- MVP라도 인증/권한/상태 변경 요청의 보안 기준을 보수적으로 잡는다.

적용 제약:

- `POST`, `PATCH`, `PUT`, `DELETE` 등 서버 상태를 바꾸는 요청은 CSRF token을 요구한다.
- 프론트 API client는 state-changing request에 CSRF header를 자동으로 포함해야 한다.
- 백엔드는 CSRF 실패와 인증 실패를 구분된 error code로 응답한다.
- SameSite cookie 정책은 CSRF token의 대체물이 아니라 보조 방어선으로 취급한다.

### 선택지

| option_id | 선택지 | 설명 | 영향 |
|---|---|---|---|
| D-130-A | cookie 인증 endpoint만 CSRF 적용 | refresh/logout처럼 cookie가 자동 전송되는 endpoint에 적용한다. | 범위가 작고 실용적이다. |
| D-130-B | 모든 state-changing endpoint에 CSRF 적용 | POST/PATCH/DELETE 전체에 적용한다. | 보수적이다. 프론트 구현 부담이 늘어난다. |
| D-130-C | Authorization header만 사용하고 CSRF 최소화 | cookie 의존을 줄이고 CSRF를 단순화한다. | 구현은 쉽지만 token 저장 정책과 함께 봐야 한다. |

### 내 추천

`D-130-A` 또는 `D-130-B`. D-120 선택에 따라 같이 정해야 한다.

## D-300. LLM 도입 단계

status: `selected`  
selected_option: `D-300-B`

### 결정

LLM은 판정 이후 요약부터 사용한다.

적용 제약:

- LLM은 결과 화면 요약, 플레이 스타일 요약, 운영자용 매치 로그 요약에 우선 사용한다.
- LLM은 행동 성공/실패, 승패, 수치 변화, 단서 획득 판정에 관여하지 않는다.
- LLM 호출이 실패해도 정적 문구와 서버 판정 결과만으로 화면을 완성할 수 있어야 한다.
- LLM 생성 결과는 공식 설정이나 룰 변경으로 취급하지 않는다.

### 선택지

| option_id | 선택지 | 설명 | 영향 |
|---|---|---|---|
| D-300-A | MVP에서 실제 LLM 호출 제외 | 정적 문구와 룰 로그만 사용한다. | 가장 안정적이다. LLM 기능 검증은 늦어진다. |
| D-300-B | 판정 이후 요약만 LLM 사용 | 결과 화면 요약, 스타일 요약 등에만 사용한다. | 위험이 낮고 LLM 가치를 일부 검증한다. |
| D-300-C | 브리핑/괴이 대사까지 LLM 사용 | RAG 근거를 붙여 서사 문장을 다양화한다. | 몰입감은 좋지만 검수와 fallback이 필요하다. |

### 내 추천

`D-300-B`. 판정 이후에만 사용하면 게임 공정성과 서버 권위를 해치지 않는다.

## D-310. RAG 도입 단계

status: `selected`  
selected_option: `D-310-B`

### 결정

RAG는 문서 검색 interface와 로그 구조를 준비하되, MVP 핵심 게임 흐름은 RAG 없이 완주 가능하게 둔다.

적용 제약:

- 초기 MVP 판정 흐름은 RAG에 의존하지 않는다.
- `retrieval` 경계는 보존하되 실제 검색 활성화는 후속 단계로 둔다.
- 나중에 LLM 요약이나 세계관 문장 생성에 RAG 근거를 붙일 수 있게 문서 ID, chunk ID, query log 구조를 고려한다.
- RAG 검색 결과는 룰, 승패, 인증, 권한 정책을 바꾸지 않는다.

### 선택지

| option_id | 선택지 | 설명 | 영향 |
|---|---|---|---|
| D-310-A | MVP에서 RAG 제외 | 정적 story data만 사용한다. | 가장 단순하다. 검색 시스템 검증은 늦어진다. |
| D-310-B | 문서 검색 interface만 준비 | retrieval 앱과 로그 구조만 만들고 실제 검색은 나중에 켠다. | 확장 준비가 된다. 구현 부담은 낮다. |
| D-310-C | 결과 요약 생성에 RAG 사용 | match 결과와 세계관 문서를 검색해 LLM 요약 근거로 쓴다. | LLM 품질이 좋아질 수 있다. 검색 품질 검증이 필요하다. |

### 내 추천

`D-310-B`. 지금은 프론트/API/룰을 먼저 맞추는 게 중요하다.

## D-401. `info_target_key` 필수 여부

status: `selected`  
selected_option: `D-401-C`

### 결정

`info_target_key`는 모든 행동 제출 요청에서 선택값으로 받을 수 있지만, 정보 행동에서는 필수다.

적용 제약:

- API request schema에는 `info_target_key`를 optional field로 둔다.
- 정보 행동은 `info_target_key`가 없으면 validation error를 반환한다.
- 비정보 행동은 `info_target_key`가 없어도 제출할 수 있다.
- 비정보 행동에 `info_target_key`가 포함되면 서버는 저장할 수 있지만, 해당 행동의 룰 효과에 사용할지는 행동별 정책을 따른다.
- 프론트는 정보 행동 선택 시 정보 대상 선택 UI를 함께 요구한다.

### 정보 행동 후보

초기 기준의 정보 행동은 아래로 둔다.

- `insight`
- `contract`
- `seal`

### 선택지

| option_id | 선택지 | 설명 | 영향 |
|---|---|---|---|
| D-401-A | 정보 관련 행동에만 필수 | `간파`, `계약`, `봉인` 등에만 `info_target_key`를 요구한다. | 자연스럽지만 API 필드 사용이 행동별로 흩어진다. |
| D-401-B | 모든 행동에 필수 | 모든 행동이 정보 대상을 함께 고른다. | 추적은 쉽지만 UX가 어색해질 수 있다. |
| D-401-C | 전체 optional, 정보 행동 필수 | 필드는 선택값이나 정보 행동에서는 필수다. | 확장성과 UX 균형이 좋다. validation rule이 필요하다. |
