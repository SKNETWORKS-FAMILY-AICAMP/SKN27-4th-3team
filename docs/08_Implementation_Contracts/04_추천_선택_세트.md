# 추천 선택 세트

이 문서는 [[08_Implementation_Contracts/03_오너_결정_워크시트]]의 빠른 검토를 돕기 위한 추천안이다.

중요: 이 문서는 확정 문서가 아니다. 아래 값은 `recommended_option`일 뿐이며, 사용자가 승인하기 전까지 워크시트의 `selected_option`에 반영하지 않는다.

## 추천 요약

| 결정 ID | 추천 옵션 | 한 줄 이유 |
|---|---|---|
| D-001 | D-001-C | 검토안과 승인본을 분리해야 팀원이 초안을 확정으로 오해하지 않는다. |
| D-010 | D-010-B | 프론트팀에는 톤만이 아니라 상태 표현 기준까지 필요하다. |
| D-020 | D-020-B | 공식 문장은 사람이 잡고 LLM은 판정 이후 변형/요약부터 쓰는 편이 안전하다. |
| D-030 | D-030-B | 공통 룰과 첫 괴이의 개성을 동시에 살릴 수 있다. |
| D-040 | D-040-B | `거울 속의 손님`의 기억 왜곡과 금기 컨셉을 가장 잘 활용한다. |
| D-100 | D-100-B | 설명용 JSONC와 도구용 strict JSON을 함께 둘 수 있다. |
| D-110 | D-110-A | 프론트/백엔드 협업 초반에는 응답 envelope 일관성이 중요하다. |
| D-120 | D-120-A 또는 D-120-B | 개발 속도는 A, 장기 보안은 B가 낫다. 이 항목은 오너 선택이 특히 필요하다. |
| D-130 | D-130-A | D-120-A를 고르면 cookie 의존 endpoint 중심 CSRF가 실용적이다. |
| D-200 | D-200-A | 기존 문서 구조와 가장 잘 맞고 책임 경계가 선명하다. |
| D-300 | D-300-B | LLM 가치를 보되 게임 판정에는 개입시키지 않는다. |
| D-310 | D-310-B | RAG 구조는 준비하되 MVP 핵심 흐름을 무겁게 만들지 않는다. |

## 1차 승인 후보

아래 묶음은 팀 병렬 진행을 시작하기 위한 최소 승인 후보이다.

### 문서 운영

recommended_option: `D-001-C`

검토안과 승인본을 분리한다.

- `08_Implementation_Contracts`: 결정 전 검토안
- `09_Approved_Contracts`: 사용자가 승인한 공통 기준

효과:

- 초안을 확정 문서로 오해하는 위험을 줄인다.
- 승인된 내용만 프론트/백엔드팀에 넘기기 쉽다.
- 문서가 하나 더 늘어나지만, 팀 커뮤니케이션 안정성이 좋아진다.

### 프론트 세계관 기준

recommended_option: `D-010-B`

프론트팀에는 아래 수준까지 제공한다.

- 핵심 톤
- 화면 감각
- 행동별 표현 방향
- 상태별 표현 방향

아직 공식 문장까지 고정하지는 않는다.

효과:

- UI 구현자는 이성, 의식력, 저주 흔적, 진명 조각, 거짓 단서를 어떻게 다룰지 감을 잡을 수 있다.
- 브리핑/승리/패배 문장은 사용자가 별도 승인할 여지를 남긴다.

### 첫 괴이 문장

recommended_option: `D-020-B`

사람이 공식 기준 문장을 작성하고, LLM은 승인된 기준 문장을 바탕으로 변형/요약을 만든다.

효과:

- 첫 MVP의 톤을 안정적으로 잡는다.
- LLM hallucination이 공식 설정을 흔드는 일을 막는다.
- 결과 화면이나 스타일 요약처럼 판정 이후 영역에서 LLM을 안전하게 검증할 수 있다.

### 진명 조각 reveal

recommended_option: `D-030-B`

행동 상성 결과와 괴이별 조건을 함께 본다.

예시:

- 공통 룰: `계약` 부분 성공 또는 `간파` 성공이 단서 진척을 만든다.
- 괴이별 조건: `거울 속의 손님`은 반복 질문, 거울 상태, 직전 정보 대상 같은 조건을 추가로 본다.

효과:

- 공통 룰 엔진을 유지하면서도 사건별 개성이 생긴다.
- 백엔드는 `game_rules`와 `story` 조건 검사를 분리할 수 있다.

### 거짓 단서 trigger

recommended_option: `D-040-B`

속임수 결과와 금기 위반이 거짓 단서를 만든다.

효과:

- `같은 질문 반복 금지`가 실제 게임 상태와 연결된다.
- 프론트는 금기 패널과 거짓 단서 UI를 자연스럽게 연결할 수 있다.

## API/Auth 추천 후보

### API 명세 포맷

recommended_option: `D-100-B`

설명용 원본은 JSONC로 유지하고, 필요하면 strict JSON을 생성한다.

효과:

- 사람이 이해하기 쉽다.
- 나중에 프론트 타입 생성, mock server, API validation에 연결할 수 있다.

### API 응답 envelope

recommended_option: `D-110-A`

성공은 `{ data, meta }`, 실패는 `{ error, meta }` 형태로 통일한다.

효과:

- request id, server time, pagination 같은 meta를 일관되게 둘 수 있다.
- 프론트 error handling이 단순해진다.

### Auth access token 전달 방식

recommended_option: `D-120-A` 또는 `D-120-B`

이 항목은 바로 하나로 밀기 어렵다.

| 후보 | 장점 | 단점 |
|---|---|---|
| D-120-A | 프론트 구현이 빠르고 디버깅이 쉽다. | access token을 JS 메모리에서 다루므로 XSS 대응 원칙이 필요하다. |
| D-120-B | JS가 토큰을 직접 다루지 않아 장기 보안성이 좋다. | CSRF와 로컬 개발 정책을 더 정확히 설계해야 한다. |

추천 판단:

- 빠른 MVP 협업이 더 중요하면 `D-120-A`
- 초반부터 보안 설계를 강하게 잡고 싶으면 `D-120-B`

### CSRF 정책

recommended_option: `D-130-A`

cookie가 자동 전송되는 refresh/logout 중심으로 CSRF를 적용하는 후보.

주의:

- `D-120-B`를 선택하면 모든 state-changing endpoint에 CSRF를 확대하는 `D-130-B`도 다시 검토해야 한다.

## 백엔드/LLM/RAG 추천 후보

### 백엔드 앱 경계

recommended_option: `D-200-A`

기존 문서처럼 아래 경계를 유지한다.

- accounts
- profiles
- game_rules
- matches
- story
- ai_profile
- llm
- retrieval
- knowledge

단, MVP 구현 우선순위는 `accounts`, `profiles`, `game_rules`, `matches`, `story`, `ai_profile`에 둔다.

### LLM 도입 단계

recommended_option: `D-300-B`

판정 이후 요약부터 LLM을 사용한다.

LLM 후보 사용처:

- 결과 화면 서사 요약
- 플레이 스타일 요약 문장
- 운영자용 매치 로그 요약

LLM 비사용 후보:

- 행동 성공/실패
- 승패
- 이성/의식력/저주 흔적 계산
- 단서 획득 판정

### RAG 도입 단계

recommended_option: `D-310-B`

retrieval interface와 로그 구조는 준비하되, MVP 핵심 게임 흐름은 RAG 없이 완주 가능하게 둔다.

효과:

- 나중에 LLM 결과 요약이나 세계관 문장 생성에 RAG를 붙일 수 있다.
- 초반 구현 복잡도는 낮춘다.

## 사용자가 바로 답하면 좋은 결정

아래처럼 답하면 다음 단계에서 워크시트에 반영할 수 있다.

```text
D-001-C 승인
D-010-B 승인
D-020-B 승인
D-030-B 승인
D-040-B 승인
D-100-B 승인
D-110-A 승인
D-120-A로 진행
D-130-A 승인
D-200-A 승인
D-300-B 승인
D-310-B 승인
```

또는 마음에 안 드는 항목만 바꿔도 된다.

```text
D-120은 B로 바꾸고, 나머지는 추천안 승인
```
