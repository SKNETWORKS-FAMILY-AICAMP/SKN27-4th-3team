# 프론트 기술 계약 오너 확정안

이 문서는 프론트 MVP 구현을 위해 오너가 확정한 기술 계약이다.

프론트팀은 이 문서를 구현 기준으로 사용할 수 있다. 단, 스토리 공식 문장, 진명 조각 reveal condition, 거짓 단서 trigger condition은 이 문서가 아니라 별도 스토리/승인 문서에서 확인한다.

## 확정 범위

이 문서는 아래 항목을 확정한다.

- 프론트 기술 스택
- 프론트 내부 폴더 구조
- 라우팅 기준
- API client 기준
- cookie 기반 인증 연결 기준
- CSRF 연결 기준
- API prefix
- 프론트 MVP endpoint 목록
- `client_request_id`, `client_nonce` 정책
- AI 스토리 시간초과 표시와 재조회 기준
- 공통 error code 기준

## 프론트 기술 스택

| 항목 | 확정값 |
|---|---|
| 프레임워크 | React |
| 언어 | TypeScript |
| 빌드 도구 | Vite |
| 라우팅 | React Router |
| 스타일 | CSS Modules |
| API client | `fetch` 기반 wrapper |
| 클라이언트 UI 상태 | React local state와 Context |
| 서버 응답 상태 | 화면/feature 단위 API hook |
| token 저장 | 저장하지 않음. HttpOnly cookie만 사용 |

MVP에서는 전역 상태 관리 라이브러리를 도입하지 않는다.

MVP에서는 API 호출을 위해 axios 같은 별도 HTTP client 의존성을 추가하지 않는다.

## 프론트 폴더 구조

프론트엔드 최상위 폴더는 `frontend/`다.

프론트 구현은 아래 구조를 기준으로 한다.

```text
frontend/
  src/
    app/
      providers/
      router/
    routes/
      login/
      signup/
      password-reset/
      lobby/
      story-cases/
      briefing/
      match/
      result/
      profile/
    features/
      auth/
      story/
      match/
      result/
      profile/
    shared/
      api/
      types/
      ui/
      constants/
      errors/
```

책임 기준:

| 경로 | 책임 |
|---|---|
| `app/providers` | 앱 전역 provider 구성 |
| `app/router` | route 정의와 보호 route 구성 |
| `routes/*` | 화면 entry component |
| `features/auth` | 로그인, 회원가입, 세션 확인 흐름 |
| `features/story` | 사건 목록, 브리핑, 정보 대상 표시 |
| `features/match` | 의식 결투 상태, 행동 제출, 턴 결과 표시 |
| `features/result` | 결과 화면, 로그, 스타일 요약 표시 |
| `features/profile` | 프로필과 전적 요약 표시 |
| `shared/api` | 공통 fetch wrapper, endpoint 함수 |
| `shared/types` | API 공통 타입과 화면 공통 타입 |
| `shared/ui` | 재사용 UI component |
| `shared/constants` | 반복 문자열, route path, action code |
| `shared/errors` | error code와 사용자 표시 문구 매핑 |

프로젝트 최상위 폴더 구조는 [[09_Approved_Contracts/23_프로젝트_폴더_구조_계약]]을 따른다.

## Route 기준

| route | 화면 | 인증 |
|---|---|---|
| `/login` | 로그인 | 비로그인 |
| `/signup` | 회원가입 | 비로그인 |
| `/password-reset` | 비밀번호 재설정 | 비로그인 |
| `/lobby` | 로비 | 로그인 |
| `/story-cases` | AI 사건 선택 | 로그인 |
| `/story-cases/mirror-guest/briefing` | `거울 속의 손님` 브리핑 | 로그인 |
| `/matches/:matchId` | 의식 결투 | 로그인 |
| `/matches/:matchId/result` | 결과 | 로그인 |
| `/profile` | 프로필 | 로그인 |

`mirror-guest`는 1차 MVP의 프론트 route slug로 사용한다.

서버의 `case_id`는 `mirror_guest` 문자열을 사용한다.

## API 기본 계약

API prefix는 아래 값으로 확정한다.

```text
/api/v1
```

성공 응답은 `{ data, meta }`, 실패 응답은 `{ error, meta }` 형태를 사용한다.

`meta`에는 최소한 아래 필드를 포함한다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `request_id` | string | 요청 추적 ID |
| `server_time` | string | ISO-8601 UTC server time |

프론트는 `error.message`를 그대로 노출하지 않아도 된다. 사용자 표시 문구는 `error.code` 기준으로 매핑한다.

## API Client 기준

프론트 API client는 `shared/api`에 둔다.

공통 client는 아래 기능을 가진다.

- base URL에 `/api/v1` 적용
- 모든 요청에 `credentials: "include"` 적용
- state-changing request에 CSRF header 자동 포함
- response envelope 처리
- error envelope 정규화
- `error.code` 기반 분기
- 401, CSRF 실패, 중복 제출 실패 구분

state-changing request는 아래 method다.

- `POST`
- `PATCH`
- `PUT`
- `DELETE`

## 인증 기준

access token과 refresh token은 모두 HttpOnly cookie로 전달한다.

프론트 기준:

- access token과 refresh token을 직접 저장하거나 읽지 않는다.
- localStorage/sessionStorage에 token을 저장하지 않는다.
- Authorization header에 Bearer token을 붙이지 않는다.
- 인증 상태는 `/api/v1/auth/me` 응답으로 확인한다.
- 401 응답을 받으면 `/api/v1/auth/refresh`를 한 번 시도한 뒤 실패 시 로그인 화면으로 이동한다.

## CSRF 기준

CSRF token 발급 endpoint는 아래 값으로 확정한다.

```text
GET /api/v1/auth/csrf
```

CSRF header 이름은 아래 값으로 확정한다.

```text
X-CSRFToken
```

프론트 기준:

- 앱 초기화 또는 첫 state-changing request 전에 CSRF token을 확보한다.
- CSRF token은 JS가 읽을 수 있는 응답 body 값으로 받는다.
- state-changing request에는 `X-CSRFToken` header를 포함한다.
- CSRF 실패 시 `/api/v1/auth/csrf`를 다시 호출한 뒤 사용자에게 재시도를 안내한다.

## Endpoint 기준

프론트 MVP에서 사용하는 endpoint는 아래 목록으로 확정한다.

| method | path | 목적 |
|---|---|---|
| `GET` | `/api/v1/auth/csrf` | CSRF token 발급 |
| `POST` | `/api/v1/auth/signup` | 회원가입 |
| `POST` | `/api/v1/auth/login` | 로그인 |
| `POST` | `/api/v1/auth/logout` | 로그아웃 |
| `POST` | `/api/v1/auth/refresh` | token refresh |
| `GET` | `/api/v1/auth/me` | 현재 사용자/session 확인 |
| `GET` | `/api/v1/story/cases` | AI 사건 목록 |
| `GET` | `/api/v1/story/cases/{case_id}/briefing` | 브리핑 조회 |
| `POST` | `/api/v1/story/cases/{case_id}/matches` | AI 스토리 매치 시작 |
| `GET` | `/api/v1/matches/{match_id}` | 현재 매치 상태 조회 |
| `POST` | `/api/v1/matches/{match_id}/turns` | 행동 제출 |
| `GET` | `/api/v1/matches/{match_id}/result` | 결과 조회 |
| `GET` | `/api/v1/profile/me` | 내 프로필과 요약 조회 |

## 요청 ID 기준

매치 시작 request에는 `client_request_id`를 포함한다.

행동 제출 request에는 `client_nonce`를 포함한다.

두 값은 모두 프론트에서 생성한 UUID 문자열이다.

서버는 같은 사용자가 같은 `client_request_id` 또는 `client_nonce`로 반복 요청할 때 중복 제출로 처리한다.

## 시간초과 연결 기준

AI 스토리 시간초과는 서버 `deadline_at` 기준으로 판정한다.

프론트는 브라우저 종료나 네트워크 끊김을 자체적으로 시간초과, 패배, 항복으로 확정하지 않는다.

프론트는 서버가 내려준 `deadline_at`으로 카운트다운을 표시할 수 있지만, 최종 턴 결과는 서버 응답을 따른다.

재접속 또는 새로고침 후에는 `GET /api/v1/matches/{match_id}`로 최신 매치 상태를 조회한다.

상세 기준은 [[09_Approved_Contracts/21_AI_스토리_시간초과_판정_계약]]을 따른다.

## 행동 제출 기준

행동 제출 request 기본 형태:

```json
{
  "action_code": "insight",
  "info_target_key": "mirror_back",
  "client_nonce": "uuid-generated-by-frontend"
}
```

정보 행동은 아래와 같다.

- `insight`
- `contract`
- `seal`

정보 행동은 `info_target_key`가 필수다.

비정보 행동에 `info_target_key`가 포함되면 서버는 저장할 수 있지만, 룰 효과에 사용할지는 행동별 정책을 따른다.

## Error Code 기준

프론트 MVP에서 최소 구분해야 하는 error code는 아래와 같다.

| code | 의미 | 프론트 처리 |
|---|---|---|
| `AUTH_REQUIRED` | 인증 필요 | 로그인 화면 이동 |
| `SESSION_EXPIRED` | 세션 만료 | refresh 시도 후 실패 시 로그인 화면 이동 |
| `CSRF_TOKEN_MISSING` | CSRF token 없음 | CSRF token 재획득 |
| `CSRF_TOKEN_INVALID` | CSRF token invalid | CSRF token 재획득 |
| `VALIDATION_ERROR` | 요청 검증 실패 | field error 또는 일반 오류 표시 |
| `MATCH_NOT_FOUND` | 매치 없음 | 로비 또는 사건 선택으로 이동 |
| `MATCH_ALREADY_FINISHED` | 이미 종료된 매치 | 결과 화면 이동 |
| `TURN_ALREADY_SUBMITTED` | 중복 제출 | 현재 턴 결과 조회 또는 대기 |
| `TURN_DEADLINE_EXPIRED` | 턴 마감 이후 제출 | 최신 매치 상태 조회 |
| `ACTION_NOT_AVAILABLE` | 행동 불가 | 서버가 내려준 사유 표시 |
| `INFO_TARGET_REQUIRED` | 정보 대상 누락 | 정보 대상 선택 유도 |
| `RATE_LIMITED` | 요청 제한 | 잠시 후 재시도 안내 |
| `LLM_SUMMARY_UNAVAILABLE` | LLM 요약 실패 | 정적 결과 문장 표시 |

## Runtime Progress Feedback 기준

의식 결투 화면은 사용자가 화면이 멈췄다고 오해하지 않도록 진행 상태를 명시한다.

- 턴 제출 직후에는 `결과 처리 중...` 상태를 표시한다.
- 서버 응답 대기가 2초 이상 길어지면 `서버 판정 대기 중...` 상태로 갱신한다.
- `TURN_DEADLINE_EXPIRED` 처리 중에는 최신 매치 상태를 다시 불러오는 상태를 표시할 수 있다.
- 판정 로그, 괴이 대사, 턴 종료 cue처럼 사용자의 입력을 기다리는 구간에는 `클릭 또는 Enter로 계속` 진행 cue를 표시한다.
- LLM 생성 실패 또는 지연은 서버 판정 결과를 막지 않는다. 화면은 정적 public log와 서버 match state로 계속 진행한다.

## 화면별 API 연결

| 화면 | 필요한 endpoint |
|---|---|
| 로그인 | `GET /auth/csrf`, `POST /auth/login`, `GET /auth/me` |
| 회원가입 | `GET /auth/csrf`, `POST /auth/signup` |
| 로비 | `GET /auth/me`, `GET /profile/me` |
| 사건 선택 | `GET /story/cases` |

| 결과 | `GET /matches/{match_id}/result` |
| 프로필 | `GET /profile/me` |
