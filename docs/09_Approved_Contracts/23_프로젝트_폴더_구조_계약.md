# 프로젝트 폴더 구조 계약

이 문서는 1차 MVP 구현을 위한 프로젝트 최상위 폴더 구조와 팀별 책임 경계를 확정한다.

## 결정

A안인 Monorepo + 팀별 경계 분리 구조를 사용한다.

프론트엔드, 백엔드, LLM 팀 작업 영역을 분리하되, 공식 API 계약과 승인 문서는 같은 저장소 안에서 공유한다.

## 최상위 구조

```text
pilot/
  backend/
  frontend/
  llm/
  api-spec/
  docs/
  tools/
  output/
  ops/
```

| 폴더 | 책임 |
|---|---|
| `backend/` | Django API, DB 모델, 서버 판정, Auth, RAG 검색 구조, AI Profile |
| `frontend/` | React + TypeScript + Vite 프론트 구현 |
| `llm/` | LLM 팀의 prompt, generation 정책, 평가 샘플, provider 실험 |
| `api-spec/` | 공식 API schema와 draft 명세 |
| `docs/` | 승인 문서, 설계 문서, 후순위 문서 |
| `tools/` | 문서 생성, 검증, 개발 보조 스크립트 |
| `output/` | 문서/이미지/PDF 같은 생성 산출물 |
| `ops/` | Docker Compose, Dockerfile, env template, 운영/배포 설정 후보 |

## Backend 구조

```text
backend/
  config/
  apps/
    accounts/
    profiles/
    game_rules/
    matches/
    story/
    ai_profile/
    retrieval/
    llm/
    knowledge/
  tests/
```

| 경로 | 책임 |
|---|---|
| `backend/config/` | Django project settings, URL routing, ASGI/WSGI 진입점 |
| `backend/apps/accounts/` | 회원가입, 로그인, 로그아웃, refresh token, 인증 이벤트 |
| `backend/apps/profiles/` | 닉네임, 전적 요약, 스타일 요약 표시 데이터 |
| `backend/apps/game_rules/` | 행동, 자원, 상성, 승패 조건의 결정적 규칙 |
| `backend/apps/matches/` | 매치, 참가자, 턴, 행동 제출, 결과 저장 |
| `backend/apps/story/` | AI 스토리 사건, 괴이, 단서, 금기, 브리핑 |
| `backend/apps/ai_profile/` | 행동 이벤트 저장, 스타일 지표 계산 |
| `backend/apps/retrieval/` | RAG 문서, chunk, embedding, 검색, query log |
| `backend/apps/llm/` | LLM 호출 경계, generation result 저장/조회 경계 |
| `backend/apps/knowledge/` | future KAG 경계. 1차 MVP 구현 제외 |
| `backend/tests/` | 백엔드 테스트 |

`backend/apps/llm/`은 LLM 팀 작업물을 서버에 연결하는 경계다.

LLM prompt 실험, 평가 샘플, provider 비교는 `backend/apps/llm/`이 아니라 최상위 `llm/`에서 관리한다.

## Frontend 구조

## LLM 팀 구조

```text
llm/
  prompts/
  generation/
  evaluation/
  fixtures/
  docs/
```

| 경로 | 책임 |
|---|---|
| `llm/prompts/` | purpose별 prompt 초안과 version 후보 |
| `llm/generation/` | generation purpose, input/output draft, provider adapter 실험 |
| `llm/evaluation/` | 품질 평가 기준, 금지선 체크, 회귀 샘플 |
| `llm/fixtures/` | match result, style metrics, retrieval context 샘플 |
| `llm/docs/` | LLM 팀 내부 설계 메모와 전달 문서 |

LLM 팀 산출물은 승인 전까지 공식 룰, 공식 문장, 서버 판정으로 취급하지 않는다.

LLM 생성 기능을 서버에 연결할 때는 `backend/apps/llm/` 경계를 통해서만 연결한다.

## Ops 구조

```text
ops/
  docker/
  env/
  scripts/
```

| 경로 | 책임 |
|---|---|
| `ops/docker/` | Docker Compose, Dockerfile, 컨테이너 실행 구성, 이미지 빌드 후보 |
| `ops/env/` | env template, 환경 변수 설명, 배포 환경 변수 후보 |
| `ops/scripts/` | 운영/개발 실행 보조 스크립트 |

1차 MVP 로컬 실행 구성은 Django API, PostgreSQL, PostgreSQL `pgvector`로 제한한다.

Redis, WebSocket worker, LLM provider emulator, KAG 전용 저장소는 1차 MVP 로컬 실행 구성에서 제외한다.

Dockerfile 기반 백엔드 이미지 빌드와 Django 배포 준비 파일도 `ops/` 경계에서 관리한다.

단, production 배포 방식은 아직 이 계약의 구현 확정 범위가 아니다.

Dockerfile 이미지 빌드와 배포 결정 타이밍은 [[09_Approved_Contracts/24_Dockerfile_이미지_빌드_배포_준비_계약]]을 따른다.

production 배포를 진행하려면 배포 대상 환경, image registry/tag, WSGI/ASGI server, static/media 처리, secret 주입, migration 실행, health check, reverse proxy/TLS, CI/CD 방식을 별도 배포 계약으로 확정한다.

## 구현 금지선

- LLM 팀 작업물을 `backend/apps/game_rules`, `backend/apps/story`, `backend/apps/matches`의 서버 판정 로직에 직접 섞지 않는다.
- 프론트엔드가 API, DB, 룰 계약을 임의 확정하지 않는다.
- `frontend/`에서 access token 또는 refresh token을 저장하는 구조를 만들지 않는다.
- `llm/`의 prompt나 generation 결과를 공식 설정 또는 공식 판정으로 취급하지 않는다.
- `backend/apps/realtime/`은 PvP 미사용 결정에 따라 목표 구조에서 제외한다. 기존 placeholder가 있으면 별도 구조 정리 작업에서 제거한다.
- `backend/apps/knowledge/`는 1차 MVP에서 구현 필수 경로로 만들지 않는다.
- `api-spec/pilot-mvp-api.official.jsonc`와 `api-spec/pilot-mvp-api.official.json`을 우회한 API shape를 구현하지 않는다.

## 실제 폴더 생성 기준

이 문서는 물리 폴더 구조의 승인 기준이다.

실제 폴더 생성은 구현 착수 시점에 이 구조를 기준으로 진행한다.

빈 placeholder 파일을 만들기 위해 불필요한 파일을 추가하지 않는다.
