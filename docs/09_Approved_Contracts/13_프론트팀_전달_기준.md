# 프론트팀 전달 기준

이 문서는 프론트팀에 전달할 승인된 작업 기준이다.

프론트팀은 이 문서를 먼저 보고, 세부 판단이 필요하면 연결된 승인본 문서를 확인한다.

## 문서 우선순위

1. `09_Approved_Contracts`의 승인본 문서를 우선한다.
2. `08_Implementation_Contracts`의 문서는 검토안이며 구현 확정 기준이 아니다.
3. `api-spec/pilot-mvp-api.jsonc`는 설명이 붙은 후보 명세이며, 승인본 API 명세가 나오기 전까지 확정 계약으로 쓰지 않는다.
4. 승인본끼리 충돌하거나 빠진 항목이 있으면 오너 확인 전까지 구현 확정하지 않는다.

## 역할 경계

오너는 아래 항목의 최종 기준을 정한다.

- 세계관 큰 틀
- 첫 스토리 핵심 구조
- 괴이 컨셉, 금기, 진명 조각, 거짓 단서 기준
- 공식 기준 문장 승인
- API, 폴더 구조, 앱 경계, 인증, 응답 형태 같은 기술 계약

프론트팀은 승인된 기준 안에서 아래 항목을 설계한다.

- 화면 흐름
- 브리핑, 결투, 결과 화면의 표현
- 문장 배치와 정보 노출 순서
- 레이아웃, 색, 질감, 아이콘, 애니메이션
- 상태 시각화 방식
- 모바일/데스크톱 화면 구조

프론트팀이 작성한 세부 흐름, 표현, 문장 후보는 오너 승인 전까지 공식 설정, 룰, 서버 판정으로 취급하지 않는다.

## 프론트팀에 전달된 확정 기준

### 제품 톤

`pilot`은 초자연 공포 스릴러 미스터리 기반 1대1 턴제 심리전 웹 게임이다.

플레이어는 괴이를 체력으로 깎아 죽이는 전투자가 아니라, 저주받은 생존자로서 괴이와 마주 앉아 진명을 파헤치고 봉인한다.

핵심 감각은 카드 배틀보다 `생존 의식 테이블`에 가깝다.

### 1차 MVP 대상

1차 MVP 구현 괴이는 `거울 속의 손님` 1종이다.

`우물 밑의 목소리`, `문밖의 어머니`는 문서화 대상이지만 1차 MVP 구현 대상이 아니다.

PvP 모드는 제공하지 않는다.

프론트팀은 PvP 화면, PvP 매칭, PvP 대기열, WebSocket 실시간 대전 진입점을 만들지 않는다.

### 서버 권위

아래 항목은 반드시 서버 응답을 기준으로 표시한다.

- 현재 이성, 의식력, 저주 흔적
- 행동 비용과 행동 가능 여부
- 턴 결과
- 진명 조각 획득 여부
- 거짓 단서 공개 여부
- 봉인 가능 여부
- 승패

프론트는 임시 애니메이션이나 예측 표시를 사용할 수 있지만, 최종 상태는 서버 응답으로 동기화한다.

### 첫 괴이 정보 대상

`거울 속의 손님`의 같은 질문 반복은 자유 텍스트가 아니라 정보 대상 key 반복으로 판정한다.

승인된 정보 대상은 아래 5개다.

| info_target_key | 의미 |
|---|---|
| `mirror_surface` | 거울 표면 |
| `mirror_back` | 깨진 거울 뒷면 |
| `missing_child_voice` | 사라진 아이의 목소리 |
| `forgotten_room` | 잊어버린 방 번호 |
| `self_reflection` | 플레이어의 비친 얼굴 |

프론트는 플레이어가 확인하려는 정보 대상을 선택할 수 있게 한다.

단, 정보 대상 선택 UI의 표현 방식은 프론트팀이 설계할 수 있다.

## 프론트팀이 설계해야 하는 것

프론트팀은 아래 산출물을 제안한다.

- 로그인, 회원가입, 로비, 사건 선택, 브리핑, 의식 결투, 결과, 프로필 화면 흐름
- `거울 속의 손님` 브리핑 화면 구성
- 의식 결투 화면의 정보 배치
- 행동 선택 UI와 정보 대상 선택 UI
- 턴 결과 공개 로그 표시 방식
- 진명 조각과 거짓 단서 표시 방식
- 봉인 가능 상태의 표시 방식
- 결과 화면에서 승패, 최종 상태, 로그, 스타일 요약을 보여주는 방식
- 모바일/데스크톱 대응 기준
- 서버 오류, 인증 만료, CSRF 실패, 중복 제출 실패의 사용자 표시 방식

## 프론트팀이 임의로 결정하지 않는 것

아래 항목은 프론트팀이 임의로 확정하지 않는다.

- 공식 세계관 추가
- 괴이 컨셉, 금기, 진명 조각, 거짓 단서 기준 변경
- 승패 판정
- 수치 변화
- 행동 비용 최종 검증
- 진명 조각 획득 여부
- 거짓 단서 진위
- 봉인 가능 여부
- API endpoint, request/response schema, error code
- 인증, CSRF, cookie, token 정책
- 폴더 구조, 앱 경계, DB 모델
- LLM/RAG 도입 범위와 생성 문장 권위
- 브라우저 종료/네트워크 끊김을 시간초과로 확정하는 방식

## 금지 표현

아래 표현은 피한다.

1. 카드 배틀, 스킬 버튼 전투, 판타지 RPG 전투 UI처럼 보이게 만들지 않는다.
2. 가챠, 보상 뽑기, 환금성 재화, 사행성 결제처럼 보이는 표현을 쓰지 않는다.
3. LLM 채팅 게임처럼 보이게 만들지 않는다.
4. 괴이를 체력 게이지로 깎아 죽이는 구조처럼 표현하지 않는다.
5. 프론트 문구나 LLM 생성 문장을 서버 판정 결과처럼 위장하지 않는다.

## LLM/RAG 담당자와의 경계

LLM/RAG는 별도 담당자가 맡을 수 있다.

프론트팀은 LLM/RAG 생성 결과를 표시할 수 있지만, 아래 기준을 지킨다.

- LLM 생성 문장과 공식 기준 문장을 구분할 수 있어야 한다.
- LLM 생성 문장을 승패, 수치 변화, 단서 진위, 봉인 가능 여부의 근거처럼 표시하지 않는다.
- LLM 요약이 실패해도 정적 문구와 서버 판정 결과만으로 화면을 완성할 수 있어야 한다.
- RAG 검색 결과를 공식 설정, 룰, API 계약으로 취급하지 않는다.
