# 프론트 화면 기준 LLM 표시 항목 답변

이 문서는 백엔드 담당자에게 전달하기 위한 프론트엔드 담당자의 답변이다.  
기준 화면은 `frontend/public/prototype/game-background.html` / `prototype/game-background.html`의 현재 게임 화면이다.

## 프론트 팀원에게 확인받을 것에 대한 답변

### 1. 실제 사용할 `display_slot` 값 목록

현재 게임 화면에 실제로 존재하는 로그 표시 영역은 3개다.

| display_slot | 실제 화면 위치 | 현재 용도 | LLM 적용 여부 |
|---|---|---|---|
| `left_protagonist_message` | 거울 왼쪽 벽면 | 플레이어 행동 후 주인공 로그 | 현재는 공식 로그 표시용 |
| `center_system_message` | 거울 위쪽 중앙 | 턴 결과 시스템 로그 | 현재는 공식 로그 표시용 |
| `right_apparition_message` | 거울 오른쪽 벽면 | 괴이 행동 후 귀신 로그 | `turn_flavor_text` 적용 가능 |

현재 구현에서 LLM 문구가 실제로 치환되는 위치는 `right_apparition_message`다.  
즉 백엔드가 `turn_flavor_text`를 내려줄 경우 우선 이 슬롯에 맞춰 내려주는 것이 가장 안전하다.

결과 화면용 문구는 화면 슬롯이 아니라 목적값으로 구분한다.

| purpose | 사용 위치 |
|---|---|
| `result_summary` | 클리어/게임오버 이후 결과 화면 요약 |
| `style_summary` | 결과 화면의 플레이 스타일 요약 |
| `match_log_summary` | 누적 로그 요약이 필요할 때 |

### 2. `turn_flavor_text` 최대 글자 수와 줄 수가 UI에 맞는지

현재 화면의 로그 박스는 실제 박스 테두리가 아니라 벽면 위에 떠 있는 문장 형식이다.  
그래서 길면 바로 산만해진다.

권장 기준은 아래와 같다.

| 구분 | 데스크톱 기준 | 모바일 기준 |
|---|---:|---:|
| 최대 줄 수 | 2줄 | 2줄 |
| 권장 글자 수 | 공백 포함 40자 이내 | 공백 포함 28자 이내 |
| 절대 상한 | 공백 포함 60자 | 공백 포함 40자 |

현재 CSS 기준으로 좌우 로그 폭은 데스크톱에서 `min(22vw, 340px)`, 모바일에서 `36vw`다.  
중앙 시스템 로그는 데스크톱에서 `min(28vw, 430px)`, 모바일에서 `46vw`다.

따라서 LLM 팀에는 `turn_flavor_text`를 “짧은 귀신 반응문 1-2줄”로 제한해달라고 전달하면 된다.

### 3. `\n` 줄바꿈을 그대로 렌더링할지

그대로 렌더링한다.

현재 로그 문단은 `white-space: pre-line`으로 처리되어 있어 `\n`이 줄바꿈으로 보인다.  
다만 LLM이 임의로 줄을 많이 나누면 화면이 흐트러지므로 최대 1개의 `\n`만 허용하는 것이 좋다.

### 4. `llm.enabled=false`일 때 LLM 영역 처리

LLM 영역을 따로 비우거나 숨기지 말고, 같은 위치에 백엔드 공식 로그를 표시하는 것이 맞다.

현재 화면은 LLM 전용 UI가 아니라 “귀신 로그 위치에 보조 문구를 덮어 쓰는 방식”이다.  
따라서 실패 시 아래 순서로 처리한다.

1. `llm.enabled=true`이고 `text`가 있으면 LLM 문구 표시
2. 아니면 `publicLog.text` 또는 백엔드 공식 귀신 로그 표시
3. 별도 실패 문구는 플레이어에게 보여주지 않음

### 5. LLM 응답 도착 방식

현재 프론트 플로우에는 늦게 도착하는 LLM 문구를 중간에 끼워 넣는 구조가 없다.

현재 진행 순서는 다음과 같다.

1. 플레이어가 카드 선택
2. 주인공 로그 1개 표시
3. Enter 또는 화면 클릭
4. 백엔드 턴 결과 수신
5. 귀신 로그 1개 표시
6. Enter 또는 화면 클릭
7. 시스템 결과 로그 1개 표시
8. Enter 또는 화면 클릭
9. 턴 종료 또는 결과 화면 전환

따라서 백엔드는 가능하면 턴 결과 응답에 LLM 문구를 같이 포함해주는 것이 좋다.

LLM이 늦게 도착할 수 있다면 프론트는 기다리지 않고 공식 로그로 진행하는 것이 맞다.  
이미 지나간 턴 화면에 뒤늦게 LLM 문구를 끼워 넣는 방식은 현재 UX와 맞지 않는다.

### 6. 로딩 UI 필요 여부

LLM 전용 로딩 UI는 필요 없다.

필요한 로딩은 백엔드의 턴 판정 응답을 기다리는 짧은 대기 상태뿐이다.  
LLM 때문에 턴 진행을 멈추면 클릭/Enter로 넘기는 현재 리듬이 끊긴다.

권장 처리:

- 턴 결과 응답 안에 LLM 문구가 있으면 사용
- 없으면 공식 로그 사용
- LLM만 늦는 경우에는 화면 대기 없음

### 7. `fallback_used`, `metadata.error_reason` 표시 필요 여부

플레이어 화면에는 표시하지 않는다.

이 값들은 개발 확인용으로만 의미가 있다.  
필요하다면 개발 중 콘솔 로그 또는 네트워크 응답에서 확인하면 된다.

권장:

- 운영 UI: 표시하지 않음
- 개발/QA: 응답 JSON 또는 콘솔에서만 확인
- 플레이어에게 `LLM 실패`, `fallback 사용` 같은 문구는 노출하지 않음

## LLM 팀에 전달해주면 좋은 것에 대한 답변

아래 내용은 백엔드가 LLM 팀에 전달하면 현재 프론트 화면과 가장 잘 맞는다.

### 1. 실제 메시지 박스 너비와 높이

현재 로그 영역은 고정 높이 박스가 아니라 벽면 위 텍스트다.

| 위치 | 데스크톱 폭 | 모바일 폭 | 높이 기준 |
|---|---:|---:|---|
| 주인공 로그 | `min(22vw, 340px)` | `36vw` | 1-2줄 |
| 귀신 로그 | `min(22vw, 340px)` | `36vw` | 1-2줄 |
| 시스템 로그 | `min(28vw, 430px)` | `46vw` | 1-2줄 |

텍스트가 길어지면 UI가 늘어나는 것이 아니라 벽면 문장처럼 보이기 어려워진다.

### 2. 모바일/데스크톱에서 허용 가능한 최대 줄 수

모바일과 데스크톱 모두 최대 2줄을 권장한다.

3줄 이상은 거울, 카드, HUD와 시선이 충돌해서 현재 화면 분위기와 맞지 않는다.

### 3. `display_slot`별 글자 수 제한

| display_slot | 권장 글자 수 | 절대 상한 |
|---|---:|---:|
| `left_protagonist_message` | 40자 | 60자 |
| `right_apparition_message` | 40자 | 60자 |
| `center_system_message` | 36자 | 55자 |

현재 LLM 우선 적용 대상은 `right_apparition_message`이므로, LLM 팀에는 이 슬롯 기준으로 먼저 맞춰달라고 전달하면 된다.

### 4. 괴이 대사와 시스템 문구를 시각적으로 구분하는 방식

현재 화면 색상 기준은 아래와 같다.

| 로그 종류 | 색상 방향 | 화면 느낌 |
|---|---|---|
| 주인공 로그 | 어두운 노란색 | 낡은 기록, 의식자의 독백 |
| 귀신 로그 | 어두운 붉은색 | 거울 속 반응, 위협 |
| 시스템 로그 | 어두운 흰색 | 턴 결과, 판정 요약 |

LLM은 귀신 대사처럼 보이게 할 수 있지만, 시스템 판정 문구처럼 보이면 안 된다.  
즉 LLM 문장은 “분위기 보조 대사”이고, 수치 변화나 승패 판정을 말하면 안 된다.

### 5. 실패 시 보여줄 기본 로그 위치

실패 시에도 같은 위치에 공식 로그를 보여준다.

예시:

- `turn_flavor_text` 실패: `right_apparition_message` 위치에 백엔드 공식 귀신 로그 표시
- `result_summary` 실패: 결과 화면에 정적 결과 요약 표시
- `style_summary` 실패: 결과 화면에 정적 스타일 문구 표시

### 6. 줄바꿈이 어색하게 보이는 사례

아래 형태는 피하는 것이 좋다.

```text
거울이
너를
기억한다
```

아래처럼 짧은 문장 1-2줄이 적합하다.

```text
거울 안쪽에서 젖은 머리카락이 흔들렸다.
너는 아직 이름을 모른다.
```

또는 더 짧게:

```text
거울 안쪽의 시선이 너를 따라붙었다.
```

## 백엔드에 전달할 최종 요청

백엔드는 턴 결과 응답에 공식 로그를 반드시 포함해주고, LLM 문구는 선택 필드로 포함해주면 된다.

권장 응답 일부:

```json
{
  "public_log": {
    "player_text": "촛불이 낮게 흔들리고, 너는 침묵을 골랐다.",
    "enemy_text": "거울 안쪽의 그림자가 입을 다물었다.",
    "system_text": "이번 턴에는 정보가 공개되지 않았다."
  },
  "llm_ui_texts": [
    {
      "enabled": true,
      "purpose": "turn_flavor_text",
      "display_slot": "right_apparition_message",
      "text": "거울 안쪽에서 젖은 머리카락이 천천히 흔들렸다.",
      "fallback_used": false,
      "metadata": {
        "status": "succeeded"
      }
    }
  ]
}
```

LLM이 실패한 경우:

```json
{
  "public_log": {
    "enemy_text": "거울 안쪽의 그림자가 입을 다물었다."
  },
  "llm_ui_texts": [
    {
      "enabled": false,
      "purpose": "turn_flavor_text",
      "display_slot": "right_apparition_message",
      "text": null,
      "fallback_used": true,
      "metadata": {
        "status": "failed",
        "error_reason": "provider_error"
      }
    }
  ]
}
```

프론트는 이 경우 `enemy_text`를 같은 위치에 표시한다.
